# latitudesh_server_reinstall (Action)

Reinstalls a [Latitude.sh](https://latitude.sh/) server: the disks are erased and the operating system is redeployed.

The `latitudesh_server` resource already reinstalls on its own when a reinstall-only attribute changes and `allow_reinstall = true`. This action covers what that path cannot: reinstalling **without changing desired state**. Use it to recover a server stuck in `failed_deployment`, to re-image on demand, or to wipe a machine before handing it to another workload.

~> **Requires Terraform v1.14 or later.** Actions are not available on earlier CLI versions.

## Example usage

```terraform
resource "latitudesh_server" "web" {
  hostname         = "web-01"
  operating_system = "ubuntu_24_04_x64_lts"
  plan             = data.latitudesh_plan.plan.slug
  project          = latitudesh_project.project.id
  site             = data.latitudesh_region.region.slug
  ssh_keys         = [latitudesh_ssh_key.ssh_key.id]
}

# A bare config reinstalls with the settings the server already has: same OS, same
# hostname, same keys. Nothing about latitudesh_server.web changes, so nothing drifts.
#
# Run it on demand, with no resource change to hang it off:
#
#   terraform apply -invoke=action.latitudesh_server_reinstall.rebuild
action "latitudesh_server_reinstall" "rebuild" {
  config {
    server_id = latitudesh_server.web.id
  }
}

# To rebuild during a normal apply, trigger the action from something that tracks
# *when* to rebuild rather than from the server itself. Bumping this variable
# reinstalls the machine; the server's own configuration stays put.
variable "reimage_generation" {
  description = "Bump to reinstall latitudesh_server.web on the next apply."
  type        = number
  default     = 1
}

resource "terraform_data" "reimage_generation" {
  input = var.reimage_generation

  lifecycle {
    action_trigger {
      events  = [after_update]
      actions = [action.latitudesh_server_reinstall.rebuild]
    }
  }
}

# Overrides are available, but each one is a value latitudesh_server does not know
# about. Change the OS here and the resource still believes it runs the old one, so
# the next plan shows a diff — and on a server with allow_reinstall = true, that diff
# reinstalls the machine a second time. Keep the two in agreement.
action "latitudesh_server_reinstall" "reimage_to_debian" {
  config {
    server_id        = latitudesh_server.web.id
    operating_system = "debian_12" # also update latitudesh_server.web.operating_system
    ssh_keys         = [latitudesh_ssh_key.ssh_key.id]
    wait_timeout     = "45m"
  }
}
```

Invoke it directly, outside of any resource change:

```sh
terraform apply -invoke=action.latitudesh_server_reinstall.rebuild
```

## Schema

### Required

- `server_id` (String) The ID of the server to reinstall.

### Optional

- `disk_layout` (Attributes List) Custom disk layout made of one or more disk groups, used instead of `raid`. Mutually exclusive with `raid` and `ipxe`. Supersedes the layout the server was deployed with. (see [below for nested schema](#nestedatt--disk_layout))
- `hostname` (String) The hostname to set on reinstall. Defaults to the server's current hostname.
- `ipxe` (String) The iPXE script to boot: either a URL pointing at the script, or the script encoded in base64. Required when `operating_system = "ipxe"`.
- `operating_system` (String) The operating system slug to install. Defaults to the server's current operating system.
- `persistent_netboot` (Boolean) Keep network boot enabled so the server iPXE-boots on every reboot instead of booting from disk. Only supported with the `ipxe` operating system.
- `raid` (String) RAID mode: `raid-0` or `raid-1`. Mutually exclusive with `disk_layout`.
- `ssh_keys` (List of String) SSH key IDs to install. An empty list installs no keys; omitting the attribute keeps the current ones.
- `user_data` (String) The ID of a `latitudesh_user_data` to apply on reinstall.
- `wait_for_ready` (Boolean) Wait for the server to finish redeploying and report `on`. Defaults to `true`; set to `false` to return as soon as the API accepts the reinstall.
- `wait_timeout` (String) How long to wait for the reinstall to finish, as a Go duration (for example `45m`). Defaults to `30m`. Ignored when `wait_for_ready` is `false`.

### Nested Schema for `disk_layout`

Required:

- `count` (Number) Number of disks to include in this group.
- `role` (String) Role of this disk group: `os`, `storage`, or `raw`.

Optional:

- `mount_point` (String) Mount point for this disk group, e.g. `/var/lib`. Required for the `storage` role.
- `raid_level` (String) RAID level for this disk group: `raid-0` or `raid-1`. Requires `count >= 2`.

## Behavior

- **Every attribute other than `server_id` is optional.** Omit one and the reinstall keeps the value the server was last deployed with, which is what makes a bare `server_id` config a plain rebuild.
- **The action does not update Terraform state.** Setting an attribute to something the target `latitudesh_server` resource does not declare leaves that resource drifted, and the next plan shows a diff — which, on a resource with `allow_reinstall = true`, would reinstall the server again. Keep the resource configuration and the action configuration in agreement.
- **`wait_for_ready` defaults to `true`**, so the action blocks until the server reports `on` and fails when it lands in `failed_deployment` or `failed_disk_erasing`. Status changes are streamed as progress events while it waits.
- **Reinstalling erases the disks.** There is no undo, and the action asks for no confirmation beyond the plan Terraform shows before applying.
