# latitudesh_server_power (Action)

Runs a power action on a [Latitude.sh](https://latitude.sh/) server: `power_on`, `power_off`, or `reboot`.

The `latitudesh_server` resource has no attribute describing power state, so these operations have no declarative home. The action is how you drive them from Terraform: nothing about desired state changes, and invoking it never drifts the resource.

~> **Requires Terraform v1.14 or later.** Actions are not available on earlier CLI versions.

## Example usage

```terraform
resource "latitudesh_server" "web" {
  hostname         = "web-01"
  operating_system = "ubuntu_24_04_x64_lts"
  plan             = data.latitudesh_plan.plan.slug
  project          = latitudesh_project.project.id
  site             = data.latitudesh_region.region.slug
}

# Run it on demand, with no resource change to hang it off:
#
#   terraform apply -invoke=action.latitudesh_server_power.reboot
#
# A reboot returns as soon as the API accepts it: it is a warm reset, so the
# server's status reads "on" the whole time and there is nothing to wait on.
action "latitudesh_server_power" "reboot" {
  config {
    server_id    = latitudesh_server.web.id
    power_action = "reboot"
  }
}

# power_on and power_off do wait: the action blocks until the server reports
# the status it drives it to ("off" here). Set wait_for_status = false to
# return as soon as the API accepts the request instead.
action "latitudesh_server_power" "power_off" {
  config {
    server_id    = latitudesh_server.web.id
    power_action = "power_off"
  }
}

# Or trigger it during a normal apply from something that tracks *when* to act.
# Bumping this variable reboots the machine; the server's own configuration
# stays put, so nothing drifts.
variable "reboot_generation" {
  description = "Bump to reboot latitudesh_server.web on the next apply."
  type        = number
  default     = 1
}

resource "terraform_data" "reboot_generation" {
  input = var.reboot_generation

  lifecycle {
    action_trigger {
      events  = [after_update]
      actions = [action.latitudesh_server_power.reboot]
    }
  }
}
```

Invoke it directly, outside of any resource change:

```sh
terraform apply -invoke=action.latitudesh_server_power.reboot
```

## Schema

### Required

- `power_action` (String) The power action to run: `power_on`, `power_off`, or `reboot`.
- `server_id` (String) The ID of the server to act on.

### Optional

- `wait_for_status` (Boolean) Wait until the server reports the status the action drives it to: `on` for `power_on`, `off` for `power_off`. Defaults to `true`; set to `false` to return as soon as the API accepts the action. Has no effect for `reboot`: a reboot is a warm reset, the server's status reads `on` throughout, and the API offers nothing to wait on.
- `wait_timeout` (String) How long to wait for the target status, as a Go duration (for example `10m`). Defaults to `15m`. Ignored when `wait_for_status` is `false` and for `reboot`.

## Behavior

- **`wait_for_status` defaults to `true`**, so `power_on` blocks until the server reports `on` and `power_off` until it reports `off`. Status changes are streamed as progress events while it waits. The reported status is refreshed by a background sync, so expect some lag between the machine changing state and the wait observing it.
- **`reboot` returns as soon as the API accepts it.** A reboot is a warm reset: power never drops, the server's status reads `on` before, during, and after, and the API reports no action progress — so there is nothing a wait could observe. `wait_for_status` and `wait_timeout` have no effect for it, and setting them raises a config warning.
- **Powering off a server does not pause billing.** The machine stays allocated to you; it is just powered down.
- **The action does not update Terraform state.** A server powered off through this action still satisfies its `latitudesh_server` resource on the next plan.
